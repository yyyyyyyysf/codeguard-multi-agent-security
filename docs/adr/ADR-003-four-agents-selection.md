# ADR-003: 四个 Agent 的划分标准（Agent Boundary Selection）

> **状态**: 已接受（2026-08-03）
> **关联**: PROJECT_RULES.md §17.2, HANDOFF.md §四

## 问题背景

设计初期讨论过"更多 Agent"的方案（如独立 CVE 扫描器、独立规则引擎、独立模板渲染等各拆一个）。Agent 数量直接影响编排复杂度、测试成本和故障面，需要明确的划分标准。

## 现状痛点

- Agent 拆多了：编排复杂度上升、模块间传递数据冗余、测试成本翻倍
- Agent 拆少了：单一 Agent 承担多职责，违反单一职责，改一处动全局
- 缺乏量化标准时，"拆几个"只能靠拍脑袋

## 可选方案

| 方案 | Agent 划分 |
|------|-----------|
| A. 细粒度（6-8 个） | 扫描器/规则引擎/渲染器各自独立成 Agent |
| B. 粗粒度（1-2 个） | 安全分析 Agent + 报告 Agent |
| C. **四 Agent（最终选择）** | 安全审计 / 冲突消解 / 迁移评估 / 报告聚合 |

## 划分标准（三条，缺一不可）

一个候选 Agent 必须**同时**满足以下三条才独立成 Agent：

1. **数据源独立**：输入/输出是完整、可独立产生和消费的数据产物（如 SecurityReport、MigrationReport）
2. **推理策略独立**：有不同于其他 Agent 的决策逻辑（规则匹配 vs 裁决 vs LLM 辅助 vs 模板渲染）
3. **降级路径独立**：自身故障有独立降级方案，不影响其他链路（迁移失败不影响安全输出）

### 按标准核验

| 候选 | 数据源独立 | 推理策略独立 | 降级路径独立 | 结论 |
|------|-----------|-------------|-------------|------|
| CVE 扫描器 | ✗ 并入安全审计 | — | — | 不独立 |
| Semgrep 扫描器 | ✗ 并入安全审计 | — | — | 不独立 |
| 规则引擎 | ✗ 被冲突消解使用 | — | — | 不独立 |
| 模板渲染 | ✗ 并入报告聚合 | — | — | 不独立 |
| 安全审计 | ✓ | ✓ 规则扫描 | ✓ 降级为空报告 | **独立** |
| 冲突消解 | ✓ | ✓ 裁决+人在回路 | ✓ 降级默认阻断 | **独立** |
| 迁移评估 | ✓ | ✓ LLM 辅助 | ✓ 降级跳过 | **独立** |
| 报告聚合 | ✓ | ✓ 模板+分级 | ✓ 降级 Markdown | **独立** |

## 最终决策

**采用方案 C：四个 Agent（安全审计、冲突消解、迁移评估、报告聚合），不多不少。**

- 该标准由用户亲自拍板，明确否决"更多 Agent"方案
- Agent 之间禁止直接调用内部逻辑，交互走事件总线 / 编排层（PROJECT_RULES §17.1）

## 落地影响

- 每个 Agent 拥有独立 Pydantic 输入/输出 Schema、独立降级策略（PROJECT_RULES §17）
- 测试边界清晰：4 个 Agent 测试独立成目录，覆盖率 84%–89%
- 新增能力时按同一标准评估是否值得新增 Agent，避免架构漂移

## 实施步骤

1. 安全审计 Agent（Module 7）✅
2. 冲突消解 Agent（Module 8）✅
3. 迁移评估 Agent（Module 9）✅
4. 报告聚合 Agent（Module 10）✅

## 遗留问题

- 后续若引入"漏洞解读/修复建议生成"，需按三条标准评估是并入报告聚合还是新增 Agent
- 人工复核（human_loop）当前作为冲突消解内部能力，不独立成 Agent（无独立数据产物）
